# 다크 모드 — 지금 상태 · 수요 · 견적 (2026-11-18)

**소유자**: 「DARKMODE 수요를 조사하고, 필요하다면 추가 하기위한 견적을 내보는 일」(`docs/work-orders/finishing-orders.md` FX5).

> **상태: 조사 · 견적만 했다.** 만들지 않았다 — 어느 안으로 갈지는 소유자가 정한다(맨 아래 「정할 것」).

## 1. 지금 상태 — 앱은 이미 OS의 어둡게를 따라가고, 판은 반쯤 깨진다

- **테마**: `src/Vn.App/App.axaml`의 `RequestedThemeVariant="Default"` — OS 설정을 따른다. Windows에서는 앱 색 설정(밝게/어둡게)을 읽고,
  켜진 채로 OS 설정을 바꿔도 따라 바뀐다(Avalonia.Win32 12.1.1).
- **어둡게 값이 있는 키는 하나뿐이다**: `ThemeBorderLowBrush`(`App.axaml`의 테마 사전). 나머지는 Fluent 테마의 기본 키를 쓰거나 코드에 박힌 색이다.
- **판의 그림은 모두 C#이 색을 박아 짓는다** — `new SolidColorBrush(...)` · `Color.Parse(...)` · 정적 붓 필드. `src` 전체에 약 140곳.

**어둡게로 그려 본 것**(헤드리스 · 창에 `RequestedThemeVariant=Dark`를 걸고 Skia로 그려 글자 대비를 쟀다 — 대비 3:1 미만인 글 조각 수):

| 화면 | 밝게 | 어둡게 |
|---|---|---|
| [구성] | 4 | 12 |
| [대본] | 25 | 30 |
| 설정 창 | 0 | 0 |

어둡게에서만 생기는 문제:

- **카드 이름이 안 보인다**(1.07:1) — 카드 바탕은 밝은 색으로 박혀 있는데 이름 글은 글자색을 정하지 않아 테마의 흰색을 물려받는다.
  [구성](`ChapterGraphView.axaml.cs`의 카드 바탕 `#FAFBFCFD`) · [대본](카드 바탕 미색 · 연파랑) 둘 다.
- **카드 글 칸**: Fluent 어둡게의 반투명 입력칸이 미색 카드 위에 겹쳐 회색이 되고, 안내 글이 1.49:1이다.
- **미니맵**: 바탕이 밝게 박혀(`GraphEditorView.axaml`의 `#F2F6F7FA`) [전체 · 50 · 100 · 150]과 배율 글이 흰색 — 1.13:1. 빈 선택지 칸의 흰 바탕 · 선 모양 막대도 같다.
- **[구성] 인스펙터의 「▾ 대사」 접기 제목이 검정 바탕에 검정 글이다**(1.00:1) — `ChapterGraphView.axaml`이 `ThemeForegroundBrush`를 다섯 번
  부르는데 이 키는 Fluent 12에도 App 리소스에도 없어 기본 검정으로 풀린다. **밝게에서는 우연히 맞아 보일 뿐인 잠재 결함이다.**
- 하이어아키 · 인스펙터 · 툴바 · 설정 창은 테마를 제대로 따른다.

함께 알아 둘 것:

- 밝게에도 대비가 낮은 곳이 이미 있다 — 장면 이름표(주황 위 흰 글 2.24:1) · 「빈 선택지」(2.54:1) · 입력 안내 글(2.1:1). 자동 대비 검사를 붙이면 이것들은
  허용 목록으로 뺀다(따로 고칠 일).
- 테마를 바꾸려면 팔레트 객체를 두고 `ActualThemeVariantChanged`에서 판을 다시 그려야 한다 — `GraphEditorView.Rebuild` · `ChapterGraphView`의 다시
  그리기 · `StoryHierarchy` · `DialogueNodeEditor`.
- 색을 그대로 고정한 시험이 둘 있다 — `SceneRootCardTests`(카드 바탕) · `ChapterRubberBandTests`(선택 파랑). 팔레트를 읽게 고친다.

### 굳은 색 — 어둡게에서 무엇을 바꾸나

| 역할 | 곳 | 어둡게에서 |
|---|---|---|
| 판 카드 바탕 · 테두리 · 호버 | 17 | **반드시 바꾼다** |
| 접힌 상자(챕터 · 장면 상자) | 8 | **바꾼다** |
| 판 위에 뜨는 것(미니맵 · 선 모양 막대 · 굽힘 손잡이) | 10 | 바탕은 바꾸고 파랑은 그대로 |
| 간선 · 철도 · 포트 · 선택지 칸 · 허브 | 28 | 중립 회색은 밝게, 흰 채움은 바탕색으로 |
| 칩 · 이름표(색 바탕에 흰 글) | 17 | 대부분 그대로(분기 칩 둘만 바꾼다) |
| 선택 · 잇기 파랑 | 16 | 그대로 |
| 뜻을 가진 글색(조건 · 스탯 · 오류 · 경고) | 24 | 대체로 그대로, 어두운 것 셋은 한 단계 밝게 |
| 분기 팔레트 | 9 | 여섯 색은 그대로(어두운 바탕 대비 3.6–5.2:1), 회색 대체색만 밝게 |
| 반투명 중립 회색(구분선 등) | 7 | 양쪽에서 대체로 된다 |
| 하이어아키 눈 아이콘 | 1 | 밝게 |

**반드시 바꿀 중립 바탕 · 글 · 선이 45–50곳, 그대로 두거나 밝기만 한 단계 올릴 뜻 색이 90곳쯤이다.**

## 2. 수요 — 비슷한 도구에서는 「고를 수 있음」이 표준

- **Twine 2** — 환경설정 Theme에서 System · Light · Dark를 고른다(System = OS를 따름). <https://twinery.org/reference/en/preferences/> · 지문 편집기 색을
  고르게 해 달라는 요청도 있다 <https://github.com/klembot/twinejs/issues/1378>
- **Inky** — 0.12.0(2021)에 편집기 어두운 테마, 0.14.1에 어두운 테마(Contrast · Focus)가 더 생겼다. 고를 수 있다. <https://www.github.com/inkle/inky/releases>
- **Yarn Spinner(VS Code)** — 밝은 · 어두운 Yarn 테마를 함께 싣고 그래프 색은 VS Code 테마를 따른다.
  <https://docs.yarnspinner.dev/write-yarn-scripts/yarn-spinner-editor/writing-yarn-in-vs-code>
- **articy:draft** — 2018년 개발사 답이 「색 구성 · UI 사용자화는 목록에 있다」 정도다(검색 요약만 봤고 articy:draft X에 들어갔는지는 확인하지 못했다).
- **같은 팀이 함께 쓰는 도구** — Unity는 요청이 이어지자 2019.4.8에서 어두운 테마를 모두에게 풀었다
  <https://support.unity.com/hc/en-us/articles/115004982743> · VS Code는 기본 테마로 Dark Modern과 Light Modern을 함께 둔다
  <https://code.visualstudio.com/updates/v1_78> · Obsidian은 기본이 「시스템에 맞춤」이다 <https://obsidian.md/help/appearance>
- **근거는 엇갈린다** — 교정 작업은 밝은 바탕의 어두운 글이 낫다는 연구가 있고(Piepenbrock 외 2014, *Ergonomics*), NN/g는 정상 시력에서는 밝게가
  낫지만 일부 저시력 사용자에게는 어둡게가 낫고 선호는 갈리며 사용자는 앱이 OS 설정을 따르기를 기대한다고 한다
  <https://www.nngroup.com/articles/dark-mode/> · <https://www.nngroup.com/articles/dark-mode-users-issues/>.

**판단**: 다크 모드는 비슷한 도구에서 **기본은 아니지만 고를 수 있는 기능으로 흔하다**. 작가가 오래 붙잡고 쓰는 도구에서는 「고를 수 있음」이 표준이다.
다만 **지금 당장의 문제는 수요가 아니라 결함이다** — 어둡게로 쓰는 Windows의 작가는 오늘 이미 카드 이름과 「대사」 제목을 읽을 수 없다.

## 3. 견적 — 단계 하나 = 커밋 하나, 전체 시험 통과

### (0) 밝게로 잠그기 — 1–2단계, 1–1.5시간

- `App.axaml`을 `RequestedThemeVariant="Light"`로, 시험 하나(OS가 어둡게여도 창은 밝게).
- 함께: 빠진 `ThemeForegroundBrush`를 App의 테마 사전(Light/Dark)에 정의한다 — 잠재 결함을 걷는다.
- 위험은 거의 없다. 대신 다크 모드인 Windows에서도 이 앱만 밝게 뜬다.

### (1) OS를 제대로 따르기 — 6단계, 14–20시간

1. 판 팔레트(Light/Dark 한 벌씩)와 XAML 쪽 키(미니맵 바탕 등)를 두고 `ActualThemeVariantChanged`에서 다시 그리게 한다 — 2–3시간
2. [대본] 판의 색 61곳을 팔레트로 옮긴다(카드 · 접힌 상자 · 칸 · 허브 · 미니맵 · 선 모양 막대) — 4–6시간
3. [구성] 판의 44곳을 옮긴다 — 3–4시간
4. 곁기둥 · 대화 상자 나머지 15곳쯤 — 1–2시간
5. 검증 시험: 두 테마 × 두 탭에 대비 검사(밝게에서 이미 낮은 곳은 허용 목록), 환경변수가 있을 때만 그림을 뽑는다 — 2–3시간
6. 눈으로 보고 다듬기(중립 회색 밝히기, 카드는 어두운 색조 바탕) · 작가 안내 — 2–3시간

위험: 밝게의 값이 한 곳이라도 바뀌면 안 된다(색을 고정한 시험 둘은 팔레트를 읽게 고친다) · 카드 글 칸은 카드 바탕이 어두워져야 제대로 보인다 ·
칩의 흰 글은 그대로 둔다 · 미니맵 사각형은 바탕과 함께 맞춘다 · 시험에서는 앱 전체가 아니라 창마다 테마를 건다(헤드리스 세션은 프로세스에 하나라 새면
다른 시험이 어둡게로 돈다).

### (2) (1) + 설정 창 「기타」에 「화면 밝기: 시스템 따라가기 / 밝게 / 어둡게」 — 8단계, 17–24시간

(1)에 두 단계를 더한다 — 앱 설정 `Theme`(이 PC의 설정 · `AppSettingsService`, 주 창을 만들기 전에 건다) · 설정 창 「기타」의 고르는 칸(누르면 바로 반영 —
「미니맵 감추기」와 같은 규칙, 테스트 손잡이와 헤드리스 시험). 위험은 낮다.

## 4. 권고 · 정할 것

1. **(0)을 지금 하기를 권한다** — 오늘 어둡게로 쓰는 Windows의 작가는 카드 이름과 「대사」 제목을 읽을 수 없다. `ThemeForegroundBrush` 결함도 함께 걷는다.
   1–1.5시간.
2. **다크 모드를 실제로 넣는 것은 작가에게서 요청이 나오면 (2)로 한 번에** — (1)만 하면 고를 수 없어 OS가 어둡게인 작가가 밝게를 원할 때 막힌다.
3. (2)로 간다면 기본값을 정해야 한다 — Twine · Obsidian처럼 「시스템 따라가기」가 무난하고, 교정 연구를 감안해 「밝게」를 기본으로 두는 것도 근거가 있다.

**검증 방법**(만들 때): 헤드리스가 이미 Skia로 실제 그림을 그리므로(`HeadlessUi`) 창에 테마를 걸고 `CaptureRenderedFrame()`으로 그림을 뽑고, 글 조각마다
글자색과 조상의 바탕을 겹쳐 WCAG 대비를 재는 시험을 붙인다(시제품이 3초 안에 돈다).
